## 본론
### 1. compose 파일 하나로 시작하기

#### `docker run` 대신 compose를 고른 이유

docker로 컨테이너를 띄워 사용하는 방법은 두 가지 입니다. 
1. 인라인 명령어로 관련 옵션들을 함께 호출하는 방법.
2. 설정 파일(yaml)에 관련 옵션들을 정의 후 파일 기반으로 명령어 호출

사실, 1번 방법이 잠깐 테스트 해보거나 이런 글에서 예시로 보여주기 위해서는 간편하고 좋습니다. 다만, 같은 옵션값을 매번 설정해주어야하기 때문에, 번거로운 단점이 있습니다. 이러한 방법 말고 위에서 이야기한 yaml 설정 파일로 컨테이너를 띄우는 방식을 docker compose라고 합니다. 저는 지속적으로 같은 옵션을 사용해야 했기에 docker compose를 사용했습니다.

ollama와 n8n을 설치 및 셋팅하기 위해서 아래와 같이 yaml 파일을 구성하였으며, 각 옵션들에 대한 설명을 해두었습니다.

```yaml
# ~/carrier/compose.yaml
# version: 3.8

services:
  ollama:
    image: ollama/ollama:latest
    container_name: ollama
    restart: unless-stopped
    ports:
      - "127.0.0.1:11434:11434"
    volumes:
      - ./ollama:/root/.ollama

  n8n:
    image: docker.n8n.io/n8nio/n8n
    container_name: n8n
    restart: unless-stopped
    ports:
      - "<서버 고정 IP>:5678:5678"
    environment:
      - N8N_PORT=5678
      - N8N_PROTOCOL=http
      - NODE_ENV=production
      - GENERIC_TIMEZONE=Asia/Seoul
      - TZ=Asia/Seoul
      - N8N_SECURE_COOKIE=false
    volumes:
      - ./n8n:/home/node/.n8n
    depends_on:
      - ollama
```

다만 이 파일은 **처음부터 이렇게 적었던 것이 아닙니다.** 처음 쓴 값 중 네 가지가 틀렸고, 위에 적은 것은 그걸 고친 뒤의 상태입니다. 무엇이 어떻게 틀렸는지도 아래에 함께 적었습니다.

<KnowledgeList title="compose 파일을 읽기 전에">
<KnowledgeNote term="compose 파일의 항목들" kind="definition" defaultOpen>

`services:` 아래에 서비스를 하나씩 적고, 그 안에 어떻게 띄울지를 씁니다. 위 파일에 쓴 것만 모으면 이렇습니다.

| 항목 | 뜻 |
|---|---|
| `image` | 어떤 **이미지**로 띄울지. `이름:태그` 형식이고 태그를 생략하면 `latest` |
| `container_name` | 컨테이너에 붙일 **이름.** 안 쓰면 `프로젝트명-서비스명-1`처럼 자동 생성됩니다 |
| `restart` | 죽거나 재부팅됐을 때 **다시 띄울지** |
| `ports` | 호스트의 어느 포트로 **내보낼지** |
| `volumes` | 호스트의 어느 경로를 컨테이너 안에 **연결할지** |
| `environment` | 컨테이너 안에 넣어줄 **환경변수** |
| `depends_on` | **먼저 시작할** 서비스 |

`services:` 아래 붙인 이름(`ollama`, `n8n`)이 두 가지 역할을 합니다. compose가 부르는 서비스 이름이면서, 동시에 **컨테이너끼리 서로를 부를 때 쓰는 호스트명**이 됩니다. 뒤에서 다시 나옵니다.

**`version: '3.8'` 같은 줄은 이제 적지 않습니다.** 예전 예제에는 파일 맨 위에 거의 항상 붙어 있는데, Compose V2부터는 이 필드를 읽지 않고 경고만 출력합니다.

</KnowledgeNote>
<KnowledgeNote term="volumes — 바인드 마운트와 명명 볼륨" kind="definition">

컨테이너 안에 쓴 파일은 **컨테이너를 지우면 같이 사라집니다.** 남겨야 하는 것은 밖으로 빼둬야 하고, 그 방법이 두 가지입니다.

```yaml
volumes:
  - ./ollama:/root/.ollama     # 바인드 마운트 — 호스트의 실제 경로
  - ollama-data:/root/.ollama  # 명명 볼륨 — Docker가 관리하는 저장소
```

| 방식 | 실제 위치 | 성격 |
|---|---|---|
| **바인드 마운트** | 내가 지정한 경로 (`./ollama`) | `ls`로 바로 보이고 백업하기 쉽습니다 |
| **명명 볼륨** | `/var/lib/docker/volumes/...` | Docker가 관리합니다. 경로를 신경 쓸 필요가 없습니다 |

이 서버는 **바인드 마운트**를 사용해보려고 합니다. 모델 파일이나 워크플로처럼 남아야 하는 것이 **어느 경로에 떨어지는지를 제가 직접 정해야 하기 때문**입니다. Docker가 알아서 두는 자리에 맡기면 그걸 통제할 수 없습니다.


`./ollama`의 `.`은 **compose 파일이 있는 디렉터리**를 뜻합니다. `~/carrier/compose.yaml`에 적었으니 `~/carrier/ollama/`가 됩니다.

</KnowledgeNote>
<KnowledgeNote term="restart 정책 네 가지" kind="definition">

컨테이너가 죽거나 서버가 재부팅됐을 때 어떻게 할지를 정합니다.

| 값 | 동작 |
|---|---|
| `no` | 아무것도 하지 않습니다. 기본값 |
| `on-failure` | **비정상 종료일 때만** 다시 띄웁니다 |
| `always` | 항상 다시 띄웁니다. `docker stop`으로 직접 멈춰도 **재부팅하면 다시 뜹니다** |
| `unless-stopped` | 항상 다시 띄우되, **직접 멈춘 것은 그대로 둡니다** |

`always`와 `unless-stopped`의 차이가 실제로 갈리는 지점은 재부팅입니다. 점검하려고 컨테이너를 내려둔 상태에서 서버를 재부팅하면, `always`는 제 의도를 무시하고 다시 띄웁니다. `unless-stopped`는 내려둔 채로 둡니다.

그래서, 이 서버는 `unless-stopped`를 씁니다. 홈서버는 전원이 나갔다 들어오는 일이 있어서 **자동으로 복구되어야 하지만**, 제가 일부러 멈춘 것까지 되살아나면 곤란하기 때문입니다.

</KnowledgeNote>
<KnowledgeNote term="주의 — 이 파일에서 처음에 틀렸던 값들" kind="caution" defaultOpen>

위 파일은 처음부터 이렇게 적었던 것이 아닙니다. **동작은 했지만 나중에 문제가 될 값**이 섞여 있었고, 네 가지를 고친 뒤의 상태입니다.

**① `N8N_HOST=0.0.0.0` — 지웠습니다.** "모든 IP의 접근을 허용한다"는 뜻으로 알고 넣었는데, 이 값은 **n8n이 자기 주소를 만들 때 쓰는 기준값**입니다. 그대로 두면 웹훅 주소가 `http://0.0.0.0:5678/webhook/...`이 됩니다. `0.0.0.0`은 "모든 인터페이스"라는 뜻의 특수 표기라 **목적지 주소로는 쓸 수 없습니다.** 접속 허용 범위를 정하는 것은 포트 바인딩과 방화벽이지 이 값이 아닙니다. 지우면 n8n이 요청에서 호스트를 추론합니다. **이름이 하는 일을 말해주지 않는 설정값**이 있습니다.

**② 시간대는 두 군데를 맞춰야 합니다.** 처음에는 `GENERIC_TIMEZONE`만 넣어두었습니다.

| 변수 | 무엇을 정하나 |
|---|---|
| `GENERIC_TIMEZONE` | n8n **스케줄러**가 해석하는 시간대 |
| `TZ` | **컨테이너 운영체제**의 시간대 |

컨테이너는 기본이 UTC이고, **호스트가 KST여도 따라오지 않습니다.** `TZ`가 UTC로 남아 있으면 스케줄은 제시간에 도는데 로그 타임스탬프가 9시간 어긋나고, Code 노드에서 `new Date()`로 날짜를 계산하면 **자정 근처에서 하루가 밀립니다.** 매일 남은 일정을 정리하는 비서라면 두 번째가 치명적인데, 스케줄이 제시간에 돌기 때문에 한동안 눈치채지 못합니다.

**③ `depends_on`은 준비를 기다려주지 않습니다.** "Ollama가 켜진 것을 확인한 뒤 n8n이 실행된다"는 뜻으로 이해했는데, 실제로는 **컨테이너가 시작됐는지만** 봅니다. 그 안의 프로세스가 요청을 받을 준비가 됐는지는 확인하지 않습니다. 실제로 기다리게 하려면 두 가지가 필요합니다.

```yaml
  ollama:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:11434"]
      interval: 10s
      retries: 5
  n8n:
    depends_on:
      ollama:
        condition: service_healthy
```

`healthcheck`가 "준비됐는지 판정하는 방법"을 정의하고, `condition: service_healthy`가 "그 판정이 통과할 때까지 기다려라"가 됩니다. 지금은 넣지 않았습니다. **n8n이 Ollama를 부르는 시점이 기동 직후가 아니라 워크플로 실행 시점**이라 실제로 문제가 되지 않기 때문입니다. 다만 **알고 두는 것과 모르고 두는 것은 다릅니다.**

**④ `N8N_SECURE_COOKIE=false` — 일부러 낮춰둔 값입니다.** n8n은 로그인 세션 쿠키에 `Secure` 속성을 붙이고, 그러면 브라우저는 **HTTPS로 접속할 때만** 그 쿠키를 보냅니다. 지금은 집 안에서 `http://<서버 고정 IP>:5678`로 접속하니, **로그인이 되는 것 같은데 계속 로그인 화면으로 돌아오는** 상태가 됩니다. 그래서 껐습니다. 같이 있는 `N8N_PROTOCOL=http`도 같은 성격입니다. **임시로 낮춰둔 것은 낮춰뒀다고 적어두어야 합니다.** 마지막 편에서 외부 접속을 열고 HTTPS를 붙이는 날 두 줄 다 되돌려야 합니다.

</KnowledgeNote>
<KnowledgeNote term="컨테이너 안의 localhost 는 다른 곳입니다" kind="caution" defaultOpen>

컨테이너는 각 컨테이너별로 네트워크 공간을 가집니다. 그래서 **컨테이너 안에서 `localhost`는 그 컨테이너 자신**을 가리킵니다. 호스트도 아니고 옆 컨테이너도 아닙니다.

```bash
curl http://localhost:11434                   # 호스트에서 — 됩니다
docker exec n8n curl http://localhost:11434   # n8n 안에서 — 안 됩니다
```

n8n 컨테이너 안에 11434를 듣고 있는 것이 없기 때문입니다. 부를 때는 **서비스 이름**을 씁니다.

```bash
docker exec n8n curl http://ollama:11434      # 됩니다
```

Compose가 프로젝트마다 네트워크를 하나 만들고 **서비스 이름을 그 네트워크의 호스트명으로 등록**해주기 때문에 가능한 일입니다. 별도로 IP를 알아낼 필요가 없고, 컨테이너를 다시 띄워 IP가 바뀌어도 이름은 그대로입니다.

두 서비스를 굳이 한 파일에 둔 이유가 여기 있습니다. **같은 프로젝트에 있어야 같은 네트워크에 들어갑니다.**

호스트 자신을 가리켜야 한다면 `host.docker.internal`이라는 별도의 이름을 씁니다.

</KnowledgeNote>
</KnowledgeList>

#### 이 글에서 반복해서 쓰는 docker 명령


| 명령 | 하는 일 |
|---|---|
| `docker compose up -d` | compose 파일대로 띄웁니다. **파일을 고친 뒤 다시 실행하면 바뀐 것만 다시 만듭니다** |
| `docker compose down` | 이 프로젝트의 컨테이너를 내립니다. 볼륨은 남습니다 |
| `docker compose logs -f <서비스>` | 로그를 이어서 봅니다 |
| `docker ps` | 지금 떠 있는 컨테이너 목록 |
| `docker logs <컨테이너>` | 그 컨테이너의 로그 |
| `docker exec <컨테이너> <명령>` | 컨테이너 **안에서** 명령을 실행합니다 |
| `docker stats` | 컨테이너별 CPU·메모리 사용량을 실시간으로 |

`-d`는 **detached**, 터미널을 붙잡지 않고 뒤로 보내라는 뜻입니다. 이게 없으면 로그가 화면에 계속 흐르고, 터미널을 닫으면 컨테이너도 내려갑니다.

`docker exec`가 이 글에서 특히 자주 나옵니다. Ollama는 컨테이너 안에서 도는 프로그램이라, 모델 목록을 보거나 명령을 주려면 밖에서 부를 방법이 필요합니다.

```bash
docker exec ollama ollama list          # 컨테이너 안의 ollama 명령을 실행
docker exec -it ollama bash             # 아예 셸을 열고 들어가기
```

`-it`는 두 옵션을 붙여 쓴 것입니다. `-i`는 입력을 계속 받겠다는 뜻(**i**nteractive), `-t`는 터미널처럼 보이게 하라는 뜻(**t**ty)입니다. 셸을 열 때는 둘 다 필요합니다.

**`docker compose`는 공백입니다.** 지난 편에서 적었듯 하이픈이 붙은 `docker-compose`는 지원이 끝난 V1입니다.

### 2. Ollama — 로컬 모델 올리기

#### Ollama가 하는 일

Ollama는 언어 모델을 내려받아 로컬에서 실행하고, 그 결과를 HTTP API로 노출해주는 도구입니다. 모델 파일 관리, 양자화 형식 해석, 메모리 배분 같은 것을 알아서 처리해줍니다.

이런 도구가 필요한 이유는, 모델 가중치 파일 하나만 있어도 그것을 실행하려면 붙여야 할 것이 많기 때문입니다. Ollama는 그 과정을 명령 하나로 줄여줍니다.

```bash
docker exec ollama ollama pull gemma4:e2b
docker exec ollama ollama list
```
```
NAME          SIZE
gemma4:e2b    7.2 GB
gemma4:e4b    9.6 GB
```

둘 다 텍스트뿐 아니라 **이미지와 오디오까지 받는 멀티모달 모델**이고, 컨텍스트는 128K입니다. 이 중 **멀티모달이라는 점이 번외편에서 발목을 잡습니다.**

<KnowledgeList title="모델을 내려받기 전에">
<KnowledgeNote term="ollama 하위 명령 읽기" kind="definition" defaultOpen>

| 명령 | 하는 일 |
|---|---|
| `ollama pull <모델>` | 모델을 **내려받기만** 합니다 |
| `ollama run <모델>` | 없으면 받고, 이어서 **대화를 시작**합니다 |
| `ollama list` | 받아둔 모델 목록 |
| `ollama ps` | **지금 메모리에 올라와 있는** 모델. 여기가 중요합니다 |
| `ollama rm <모델>` | 모델 파일을 지웁니다 |

`list`와 `ps`가 헷갈리기 쉬운데, 리눅스의 `ls`와 `ps` 관계와 같습니다. **`list`는 디스크에 있는 것, `ps`는 지금 돌고 있는 것**입니다.

`ollama ps`에는 `PROCESSOR`라는 열이 있습니다. 그 모델이 지금 **CPU로 돌고 있는지 GPU로 돌고 있는지**를 비율로 보여줍니다. [번외편](/blog/home-server-extra-gpu)의 GPU 이야기에서 결정적인 명령이 됩니다.

측정할 때는 `--verbose`를 붙입니다.

```bash
docker exec -it ollama ollama run gemma4:e2b --verbose
```

이걸 붙이면 응답이 끝난 뒤에 소요 시간과 속도가 함께 출력됩니다.

</KnowledgeNote>
<KnowledgeNote term="모델 이름 읽는 법 — gemma4:e2b" kind="definition">

`이름:태그` 구조는 Docker 이미지와 같습니다. 콜론 뒤가 **어떤 변형인지**를 나타냅니다.

`e2b`, `e4b`의 **`b`는 billion, 파라미터 개수**입니다. 파라미터는 모델이 학습으로 얻은 숫자들이고, 이게 많을수록 대체로 품질이 좋고 대신 무겁습니다. 흔히 보는 `1b`, `7b`, `70b`가 그 숫자입니다.

앞에 붙은 **`e`는 유효(effective) 파라미터**를 뜻합니다. 전체 파라미터는 더 많은데, **돌릴 때 그만큼을 다 들고 있지 않아도 되도록** 만든 구조라서 그 기준으로 이름을 붙인 것입니다.

| 태그 | 전체 파라미터 | 유효 파라미터 |
|---|---|---|
| `e2b` | 약 5.1B | 약 2.3B |
| `e4b` | 약 8B | 약 4.5B |

이게 가능한 이유는 **레이어별 임베딩**(PLE, Per-Layer Embedding)입니다. 각 디코더 레이어가 토큰마다 쓸 작은 임베딩을 따로 갖는 구조인데, 이 표들은 크기는 커도 **조회에만 쓰이기 때문에** 가속기 메모리에 함께 올려둘 필요가 없습니다. 그래서 "돌리는 데 드는 몫"이 전체 파라미터보다 작아집니다.

다만 반대 방향으로 착각하면 안 됩니다. 구글 문서도 **정적 가중치를 올리는 데 필요한 총 메모리는 유효 파라미터 수가 시사하는 것보다 크다**고 적어두었습니다. `e2b`라고 해서 일반적인 2B 모델만큼 가볍지는 않습니다.

**디스크 용량, 로딩에 필요한 메모리, 추론 중에 실제로 쓰는 메모리가 전부 다릅니다.** 얼마인지는 `ollama ps`와 로그로 확인해야 합니다.

</KnowledgeNote>
<KnowledgeNote term="양자화(quantization)란" kind="definition">

같은 모델인데 파일 크기가 여러 가지로 배포되는 이유입니다.

모델의 파라미터는 원래 숫자 하나에 16비트 또는 32비트를 씁니다. **양자화는 그 정밀도를 낮춰 4비트나 8비트로 다시 저장하는 것**입니다. 소수점 아래를 잘라내는 것과 비슷합니다.

- **파일이 작아집니다.** 16비트를 4비트로 줄이면 대략 4분의 1이 됩니다
- **메모리를 적게 씁니다.** 8GB RAM 같은 환경에서는 이게 되느냐 안 되느냐를 가릅니다
- **품질이 조금 떨어집니다.** 다만 4비트 정도까지는 체감 차이가 크지 않다고 알려져 있습니다

`q4_K_M` 같은 꼬리표가 붙은 모델 이름을 본 적이 있다면 그게 양자화 방식 표시입니다. **`Q`는 양자화, `4`는 4비트, `K`는 압축 방식, `M`은 중간 품질**이라는 뜻입니다.

Ollama는 태그를 생략하면 대체로 이 `Q4_K_M` 버전을 받아옵니다. 위에서 받은 `gemma4:e2b`도 그렇고, 목록의 7.2GB가 **이미 양자화된 뒤의 크기**입니다. 그래서 대부분 신경 쓸 일이 없지만, **"파라미터 수가 같은데 왜 용량이 다르지"** 싶을 때의 답이 보통 이것입니다.

이 노트북처럼 메모리가 빠듯한 환경에서는 양자화가 선택이 아니라 전제입니다.

</KnowledgeNote>
</KnowledgeList>

### 3. n8n — 자동화 도구 올리기

#### 왜 n8n인가

n8n은 화면에서 노드를 연결해 자동화 흐름을 만드는 도구입니다. Zapier나 Make와 같은 종류인데, 결정적인 차이가 하나 있습니다. **직접 호스팅할 수 있습니다.**

Zapier에 데이터를 흘려보내면 그 데이터는 그쪽 서버를 거칩니다. 클라우드에 보내지 않으려고 집에 서버를 세워놓고, 정작 자동화 도구가 데이터를 밖으로 보내면 앞뒤가 맞지 않습니다. n8n은 같은 서버 안에서 돌면서 옆 컨테이너의 Ollama를 호출합니다. **데이터가 이 노트북을 벗어나지 않습니다.**

#### 첫 접속

`docker compose up -d` 후 브라우저에서 `5678` 포트로 접속하면 오너 계정을 만드는 화면이 나옵니다. 예전 버전에서 쓰던 `N8N_BASIC_AUTH_*` 환경변수는 이제 필요 없고, n8n 자체 사용자 관리로 대체됐습니다.

`./n8n` 볼륨에 워크플로와 자격 증명이 저장됩니다. **이 디렉터리를 잃으면 만들어둔 워크플로가 전부 사라집니다.** 백업 대상 목록의 첫 줄에 올려두어야 할 디렉터리입니다.

compose에 적어둔 n8n 환경변수 중 네 가지는 처음에 잘못 썼던 값들입니다. 무엇이 어떻게 틀렸는지는 **1절의 compose 파일 설명에 함께 적어두었습니다.**

### 4. 켜져 있다고 믿은 방화벽

#### ufw에 포트를 열었습니다

n8n을 브라우저로 열려면 5678 포트가 열려 있어야 합니다. [2편](/blog/home-server-02-security-docker)에서 ufw는 **기본 거부 상태 그대로** 두었으니, 이제 열어줘야 할 차례라고 생각했습니다.

```bash
sudo ufw allow 5678/tcp
sudo ufw allow 11434/tcp
sudo ufw status
```

그리고 브라우저에서 접속이 됐습니다. **여기서 끝났다고 생각했습니다.**

#### 그런데 밖에서는 어떻게 보이는가

컨테이너가 실제로 어떤 주소에 열려 있는지 확인해봤습니다.

```bash
docker ps --format "table {{.Names}}\t{{.Ports}}"
```
```
NAMES     PORTS
n8n       0.0.0.0:5678->5678/tcp
ollama    0.0.0.0:11434->11434/tcp
```

`0.0.0.0` — **모든 네트워크 인터페이스에 열려 있습니다.**

그리고 확인해보니, 이건 제가 ufw를 열어줬기 때문이 아니었습니다. **ufw에서 무엇을 막아두었든 상관없이 열려 있었습니다.**

```bash
sudo ufw deny 11434/tcp   # 막아봐도
```

여전히 접속됩니다. **규칙이 틀린 게 아니라 규칙에 도달하지 않습니다.**

이유는 Docker가 포트를 게시하는 방식에 있습니다. `ports: - "5678:5678"`을 선언하면 Docker는 iptables의 `DOCKER` 체인에 규칙을 직접 넣습니다. 그리고 **이 체인은 ufw가 관리하는 체인보다 먼저 평가됩니다.** ufw는 자기가 모르는 규칙이 앞에 끼어든 것을 알지 못하고, 사용자는 `ufw status`만 보고 안전하다고 착각합니다.

지난 편의 표현을 그대로 가져오면, **설정한 것과 실제로 적용된 것이 다른데 아무도 에러를 내지 않는** 상황이 또 나온 것입니다. 이번에는 방화벽이었습니다.

특히 문제가 되는 쪽은 Ollama입니다. **11434 포트에는 인증이 없습니다.** 집 안 네트워크의 아무 기기나 접속해서 모델을 부르고, 지우고, 새로 받을 수 있습니다.

<KnowledgeList title="포트가 열리는 구조">
<KnowledgeNote term="ports 표기 읽는 법" kind="definition" defaultOpen>

compose의 `ports`는 콜론으로 나뉜 자리마다 뜻이 다릅니다.

| 표기 | 뜻 |
|---|---|
| `"5678"` | 컨테이너 포트만. 호스트 쪽은 **아무 번호나 임의로** 배정됩니다 |
| `"5678:5678"` | `호스트:컨테이너`. 호스트의 **모든 인터페이스**(`0.0.0.0`)에 엽니다 |
| `"127.0.0.1:11434:11434"` | `호스트IP:호스트:컨테이너`. **지정한 주소에만** 엽니다 |

**앞자리를 생략하면 `0.0.0.0`이 됩니다.** 즉 아무 생각 없이 `"5678:5678"`이라고 쓰면 모든 곳에 여는 것입니다. 대부분의 예제가 이렇게 적혀 있고, 그래서 대부분의 홈서버가 이 상태로 돌아갑니다.

두 자리는 서로 달라도 됩니다. `"8080:5678"`은 컨테이너의 5678을 호스트의 8080으로 내보낸다는 뜻입니다. 컨테이너 안쪽 번호는 그 프로그램이 정한 것이라 바꿀 수 없지만, **호스트 쪽은 마음대로 고를 수 있습니다.**

</KnowledgeNote>
<KnowledgeNote term="왜 ufw 로는 막을 수 없는가" kind="definition">

리눅스의 방화벽은 **규칙을 순서대로 검사하는 체인** 구조입니다. 위에서부터 훑다가 맞는 규칙을 만나면 거기서 결정이 끝나고, 뒤는 보지 않습니다.

ufw는 이 체인을 다루기 쉽게 감싼 **도구**일 뿐이고, 실제 규칙은 그 아래 `iptables`(요즘은 `nftables`)에 들어갑니다. 문제는 Docker도 같은 곳에 규칙을 넣는데, **ufw의 규칙보다 앞자리에 넣는다**는 것입니다.

```
들어온 패킷
   ↓
DOCKER 체인    ← Docker가 넣은 규칙. 여기서 통과 결정이 나면 끝
   ↓
ufw 체인       ← 여기까지 오지 않습니다
```

그래서 `ufw deny 5678`을 넣어도 아무 일이 일어나지 않습니다. 그리고 `ufw status`는 **자기가 아는 규칙만** 보여주므로, 목록은 여전히 안전해 보입니다.

Docker가 이렇게 하는 데는 이유가 있습니다. 컨테이너는 수시로 뜨고 지는데, 그때마다 사용자의 방화벽 설정을 건드리는 것보다 자기 영역을 따로 관리하는 편이 안전하기 때문입니다. **버그가 아니라 설계입니다.** 그래서 고치려 들지 말고, 애초에 좁게 여는 쪽이 맞습니다.

`DOCKER-USER` 체인에 규칙을 넣어 제어하는 방법도 있지만, **바인딩 주소를 좁히는 쪽이 훨씬 단순하고 실수할 여지가 적습니다.**

</KnowledgeNote>
<KnowledgeNote term="열려 있는지 확인하는 세 가지 방법" kind="definition">

`ufw status`를 믿을 수 없다면 무엇을 봐야 하는가. 세 가지가 서로 다른 층을 보여줍니다.

```bash
sudo ufw status                                      # ① ufw 가 아는 규칙
docker ps --format "table {{.Names}}\t{{.Ports}}"    # ② Docker 가 게시한 포트
sudo ss -tulpn                                       # ③ 실제로 듣고 있는 소켓
```

**③이 최종 답입니다.** 지난 편에서 SSH 포트를 옮길 때 썼던 그 명령입니다. 설정 파일이 무엇이라고 적혀 있든, 실제로 지금 무엇이 어느 주소를 잡고 있는지를 보여줍니다.

`ss -tulpn`의 출력에서 볼 것은 **주소 부분**입니다.

| 표시 | 뜻 |
|---|---|
| `0.0.0.0:5678` | 모든 인터페이스. 집 안 아무 기기나 닿습니다 |
| `127.0.0.1:11434` | 서버 자신만. 밖에서는 닿지 않습니다 |
| `<서버 고정 IP>:5678` | 그 주소로 들어온 것만 |

</KnowledgeNote>
</KnowledgeList>

#### 바인딩 주소를 좁히기

해결책은 ufw와 싸우는 것이 아니라, **포트를 게시할 때 바인딩 주소를 좁히는 것**입니다.

```yaml
  ollama:
    ports:
      - "127.0.0.1:11434:11434"      # 서버 자신에게만
  n8n:
    ports:
      - "<서버 고정 IP>:5678:5678"      # 집 안에서 브라우저로 접속
```

Ollama는 호스트에 열어둘 이유가 **아예 없습니다.** 앞에서 본 대로 n8n은 같은 Docker 네트워크 안에서 `http://ollama:11434`로 부르기 때문에, 호스트를 거칠 일이 없습니다. 인터페이스를 특정하면 Docker가 iptables에 넣는 규칙 자체가 좁아지므로, ufw와 충돌할 일이 사라집니다.

```
n8n      <서버 고정 IP>:5678->5678/tcp
ollama   127.0.0.1:11434->11434/tcp
```

`0.0.0.0`이 사라졌습니다. 지금은 포트포워딩이 없어서 인터넷에 노출되지는 않지만, **마지막 편에서 Cloudflare Tunnel을 붙일 때 이 상태로 두면 안 됩니다.**

한편 조금 전에 넣은 ufw 규칙들은 이제 **아무 일도 하지 않습니다.** 애초에 Docker가 우회하고 있었으니 막은 적이 없고, 바인딩을 좁힌 지금은 열어줄 것도 없습니다. 규칙이 있으니 뭔가 관리되고 있다는 인상만 남습니다.

```bash
sudo ufw status numbered      # 번호 확인
sudo ufw delete <번호>         # 큰 번호부터 지웁니다
```

<KnowledgeNote term="ufw delete 는 큰 번호부터" kind="caution">

`ufw delete <번호>`로 규칙을 지울 때 **번호는 지울 때마다 다시 매겨집니다.** 3번을 지우면 4번이 3번이 됩니다.

그래서 여러 개를 지울 때 작은 번호부터 지우면 **엉뚱한 규칙이 지워집니다.** 항상 **큰 번호부터** 내려오거나, 하나 지울 때마다 `status numbered`를 다시 확인해야 합니다.

아무것도 듣고 있지 않은 포트의 규칙도 같이 정리했습니다. 규칙이 남아 있으면 **나중에 그 목록을 보는 사람(대개 몇 달 뒤의 저)이 "이건 필요해서 열어둔 것"이라고 읽습니다.** 쓰지 않는 규칙은 지워두는 편이 낫습니다.

</KnowledgeNote>

#### 그런데 이 한 줄이 다음 장애를 예약해두었습니다

방금 compose에 IP를 직접 적었습니다. 그러고 보니 지난 편에서 한 번 더 적었습니다. 맥의 `~/.ssh/config`에 넣은 `HostName`입니다.

**설정 파일에 IP를 적는 순간 그 주소가 안 바뀐다고 가정한 것**인데, 확인해본 적이 없었습니다.

```bash
ip -4 addr show eno1 | grep inet    # eno1 은 인터페이스 이름. `ip -br addr` 로 확인
```
```
inet <DHCP로 받은 IP>/24 metric 100 ... scope global dynamic eno1
```

`dynamic`. **공유기에게 빌려 쓰는 주소**입니다. 임대가 만료되거나 공유기를 재시작하면 다른 주소를 받을 수 있습니다.

그러면 무슨 일이 생기냐면, Docker는 **존재하지 않는 주소에는 바인딩할 수 없습니다.**

```
Error: bind: cannot assign requested address
```

n8n 컨테이너가 뜨지 못합니다. `restart: unless-stopped`도 소용없습니다. 그저 재시작을 반복할 뿐입니다.

그리고 이건 오늘 확인해봐야 알 수 없는 종류의 문제입니다. **지금은 아무 이상이 없고, 조건이 갖춰지는 날에만 터집니다.** 앞의 것들이 "확인하지 않아서 몰랐던 것"이라면, 이건 **확인할 대상이 아직 존재하지 않는 경우**입니다.

정공법은 공유기에서 MAC 주소에 IP를 예약하는 것인데, 공유기 관리자 페이지 로그인이 되지 않아 서버 쪽에서 해결했습니다. 다만 흔한 방법인 `dhcp4: false` + 고정 IP는 쓰지 않았습니다. **적용하는 순간 주소가 바뀌면서 SSH가 끊기고**, 헤드리스 서버라 잘못되면 노트북을 직접 열어야 하기 때문입니다.

대신 DHCP를 그대로 두고 주소를 하나 더 붙였습니다.

```yaml
# /etc/netplan/00-installer-config.yaml
    eno1:
      dhcp4: true
      addresses:
        - <서버 고정 IP>/24
```

```bash
sudo netplan generate && sudo netplan apply
```

```
inet <서버 고정 IP>/24 scope global eno1
inet <DHCP로 받은 IP>/24 metric 100 scope global secondary dynamic eno1
```

DHCP로 받은 쪽은 공유기가 주는 주소라 바뀔 수 있고, 새로 붙인 쪽은 **서버가 스스로 갖는 주소**라 바뀌지 않습니다. 게이트웨이와 DNS는 DHCP가 계속 제공하므로 따로 적을 것도 없습니다. **기존 접속이 끊기지 않으니 잠길 위험도 없습니다.**

<KnowledgeList title="netplan 을 만지기 전에">
<KnowledgeNote term="netplan 이란" kind="definition" defaultOpen>

Ubuntu에서 **네트워크 설정을 담당하는 계층**입니다. YAML 파일에 원하는 상태를 적어두면, netplan이 그것을 실제로 네트워크를 제어하는 도구(서버에서는 보통 `systemd-networkd`)의 설정으로 **번역해서 넘깁니다.**

설정 파일은 `/etc/netplan/` 아래에 있고, 이름은 설치 방식에 따라 다릅니다.

```bash
ls /etc/netplan/
```

**들여쓰기에 민감합니다.** YAML이라 공백 두 칸이 틀리면 다른 뜻이 되고, 탭 문자는 아예 허용되지 않습니다. 그래서 적용 명령이 여러 단계로 나뉘어 있습니다.

| 명령 | 하는 일 |
|---|---|
| `netplan generate` | 설정을 **번역만** 해봅니다. 문법이 틀리면 여기서 멈춥니다 |
| `netplan apply` | 실제로 적용합니다 |
| `netplan try` | 적용하되, **120초 안에 엔터를 안 누르면 자동으로 되돌립니다** |

`generate`를 먼저 하는 것은 지난 편에서 `sshd -t`를 먼저 하는 것과 같은 이유입니다. **원격 접속을 끊어먹을 수 있는 설정은 항상 검사부터** 합니다.

원격으로 네트워크를 바꿀 때는 `netplan try`가 더 안전합니다. 설정이 잘못돼 접속이 끊기면 아무것도 하지 않아도 2분 뒤에 원래대로 돌아옵니다. **되돌릴 길을 남겨두고 작업한다**는 원칙이 여기서도 그대로 적용됩니다.

</KnowledgeNote>
<KnowledgeNote term="ip addr 출력에서 봐야 할 단어" kind="definition">

```
inet <서버 고정 IP>/24 scope global eno1
inet <DHCP로 받은 IP>/24 metric 100 scope global secondary dynamic eno1
```

| 단어 | 뜻 |
|---|---|
| `inet` | IPv4 주소. IPv6은 `inet6`으로 나옵니다 |
| `/24` | 넷마스크. 앞 24비트가 같으면 같은 네트워크라는 뜻 |
| `scope global` | 외부와 통신 가능한 주소. `scope host`는 자기 자신용(`127.0.0.1`) |
| `dynamic` | **DHCP로 빌린 주소.** 만료되면 바뀔 수 있습니다 |
| `secondary` | 이 인터페이스의 **두 번째 이후** 주소 |
| `metric` | 경로 우선순위. 낮을수록 먼저 씁니다 |

여기서 결정적인 단어가 **`dynamic`** 입니다. 이게 붙어 있으면 그 주소는 **언젠가 바뀝니다.** compose 파일이나 설정에 적어 고정된 값처럼 쓰고 있다면, 그날이 장애가 나는 날입니다.

`-4`는 IPv4만 보겠다는 옵션입니다. 붙이지 않으면 IPv6 주소가 함께 나와 출력이 길어집니다.

</KnowledgeNote>
<KnowledgeNote term="고정 주소는 DHCP 범위 밖에서 골라야 합니다" kind="caution">

고정 주소를 아무 번호나 고르면 안 되는 이유가 있습니다.

공유기는 DHCP로 나눠줄 주소의 **범위**를 정해두고 그 안에서 배분합니다. 그 범위 안의 주소를 서버에 고정으로 박으면, **서버가 꺼져 있는 동안 다른 기기가 같은 주소를 받아갈 수 있습니다.** 공유기는 그 주소가 예약됐다는 걸 모르기 때문입니다.

그리고 서버가 다시 켜지면 **같은 주소를 쓰는 기기가 두 대**가 됩니다. 이걸 IP 충돌이라고 하고, 증상이 고약합니다. 완전히 끊기는 게 아니라 **어떤 요청은 되고 어떤 요청은 안 되는** 상태가 되기 때문에 원인을 찾기 어렵습니다.

그래서 **DHCP 범위 밖의 번호**를 골라야 합니다. 범위는 공유기 관리자 페이지에서 확인할 수 있습니다. 흔히 `192.168.0.100 ~ 192.168.0.200` 같은 식으로 잡혀 있고, 그 바깥의 번호를 쓰면 됩니다.

</KnowledgeNote>
</KnowledgeList>
### 5. 첫 파이프라인 — RSS에서 Discord까지

#### 두 도구가 이어지는지부터 확인하기

설치가 끝났으니 흐름이 실제로 이어지는지 확인해야 합니다. 비서를 만들기 전에, **Ollama와 n8n이 서로 연결되는지**부터 보는 단계입니다.

```
  [Schedule Trigger]   매일 아침 10시
          ▼
  [RSS Read]           Google News RSS
          ▼
  [Aggregate]          흩어진 항목을 하나로 모음
          ▼
  [Code / JavaScript]  기사 정리 · 메시지 조립
          ▼
  [Loop]  ──▶  [HTTP Request]   Discord 웹훅으로 나눠 전송
```

**처음 그렸던 흐름은 이것보다 짧았습니다.** "정해진 시간에 뉴스를 읽어서 Discord로 보낸다" 세 칸이면 될 줄 알았는데, 실제로 돌려보니 가운데에 두 개가 더 필요했습니다.

`Aggregate`가 필요했던 이유는 n8n이 데이터를 다루는 방식 때문이고, `Loop`가 필요했던 이유는 Discord 쪽 제약 때문입니다. **둘 다 만들기 전에는 보이지 않는 종류였습니다.**

<KnowledgeList title="n8n 노드 읽기">
<KnowledgeNote term="n8n 은 아이템 단위로 흐릅니다" kind="definition" defaultOpen>

n8n을 처음 만질 때 가장 헷갈렸던 개념입니다. 노드와 노드 사이를 흐르는 것은 **하나의 값이 아니라 아이템(item)의 목록**입니다.

RSS를 읽으면 기사 20개가 나옵니다. 이때 다음 노드로 넘어가는 것은 "기사 20개가 담긴 덩어리 하나"가 아니라 **아이템 20개**입니다.

그리고 중요한 성질이 있습니다. **뒤에 붙은 노드는 아이템마다 한 번씩 실행됩니다.** 그래서 RSS 뒤에 바로 HTTP Request를 붙이면, 요청이 한 번이 아니라 **20번** 나갑니다. Discord에 메시지 20개가 따로 올라갑니다.

`Aggregate` 노드는 그 반대를 합니다. **여러 아이템을 하나로 합칩니다.**

```
[RSS Read]  →  아이템 20개
[Aggregate] →  아이템 1개 (안에 20개가 배열로 들어 있음)
[Code]      →  한 번만 실행됨
```

"왜 이 노드가 여러 번 실행되지" 싶을 때는 대부분 앞에서 아이템이 여러 개로 갈라져 있는 것입니다. **개수를 의식하면서 흐름을 읽어야 합니다.**

</KnowledgeNote>
<KnowledgeNote term="Schedule Trigger 와 크론 표기" kind="definition">

워크플로를 **시작시키는 노드**입니다. n8n의 워크플로에는 반드시 시작점이 하나 있어야 하고, 종류는 몇 가지입니다.

| 트리거 | 언제 시작하나 |
|---|---|
| **Manual** | 화면에서 실행 버튼을 누를 때. 만드는 동안 씁니다 |
| **Schedule** | 정해진 시각·주기마다 |
| **Webhook** | 외부에서 특정 주소로 요청이 올 때 |

이번에 쓸 트리거는 **Schedule**입니다. 화면에서 "매일 / 10시"처럼 고를 수도 있고, 크론 표기를 직접 쓸 수도 있습니다.

```
0 10 * * *      매일 10시 정각
0 9,18 * * *    매일 9시와 18시
*/30 * * * *    30분마다
0 10 * * 1-5    평일 10시
```

다섯 자리는 앞에서부터 **분 · 시 · 일 · 월 · 요일**입니다. `*`는 "매번", `*/n`은 "n마다", `-`는 범위, `,`는 나열입니다.

여기서 **시간대가 1절에서 본 `GENERIC_TIMEZONE`을 따릅니다.** 그 값이 UTC로 남아 있으면 "매일 10시"가 한국 시간 저녁 7시가 됩니다. 설정 하나가 다른 곳에서 결과로 나타나는 자리입니다.

</KnowledgeNote>
<KnowledgeNote term="RSS 란" kind="definition">

**웹사이트가 새 글 목록을 기계가 읽기 좋은 형태로 내놓는 규약**입니다. 사이트마다 `/rss`나 `/feed` 같은 주소가 있고, 열어보면 XML이 나옵니다.

```xml
<item>
  <title>기사 제목</title>
  <link>https://...</link>
  <pubDate>...</pubDate>
</item>
```

자동화의 입력으로 편한 이유가 있습니다.

- **인증이 필요 없습니다.** API 키를 발급받거나 로그인할 필요가 없습니다
- **구조가 정해져 있습니다.** 제목·링크·날짜의 자리가 고정이라 파싱이 단순합니다
- **크롤링이 아닙니다.** 사이트가 스스로 제공하는 것이라 막힐 걱정이 적습니다

첫 파이프라인의 입력으로 RSS를 고른 것도 그래서입니다. **연결이 되는지 확인하는 게 목적인데 입력부터 씨름하면 무엇이 문제인지 가려낼 수 없습니다.** 가장 단순한 입력으로 시작해야 나머지가 보입니다.

Google News는 검색어를 넣은 RSS 주소를 제공하므로, 관심 주제만 걸러 받을 수 있습니다.

</KnowledgeNote>
<KnowledgeNote term="Code 노드와 Loop Over Items" kind="definition">

**Code 노드**는 흐름 중간에 JavaScript(또는 Python)를 끼워 넣는 자리입니다. 노드만으로 표현하기 번거로운 가공을 여기서 합니다. 이 워크플로에서는 기사 목록을 사람이 읽을 문장으로 조립하고, **글자 수에 맞춰 잘라 나누는** 일을 했습니다.

실행 방식이 두 가지인데 이걸 구분해야 합니다.

| 모드 | 동작 |
|---|---|
| **Run Once for All Items** | 전체 아이템을 한 번에 받아 **한 번** 실행 |
| **Run Once for Each Item** | 아이템마다 **각각** 실행 |

앞에서 `Aggregate`로 하나로 모았다면 전자가 자연스럽습니다.

**Loop Over Items**(예전 이름 Split In Batches)는 반대로 **여러 개를 하나씩 차례로 흘려보내는** 노드입니다. 뒤에 붙은 노드를 한 번에 하나씩만 실행시키고, 다 돌면 다음으로 넘어갑니다.

한꺼번에 보내면 되는데 굳이 이렇게 하는 이유는 **받는 쪽에 제한이 있을 때**입니다. 요청 수 제한이 걸려 있거나, 순서를 지켜야 하거나, 한 번에 보낼 수 있는 양이 정해져 있는 경우입니다. 지금이 마지막 경우입니다.

</KnowledgeNote>
<KnowledgeNote term="Discord 웹훅과 글자 수 제한" kind="definition">

**웹훅**(webhook)은 "이 주소로 POST를 보내면 그 채널에 메시지를 올려주겠다"는 일회성 주소입니다. Discord 채널 설정에서 만들 수 있고, 봇을 등록하거나 토큰을 관리할 필요가 없습니다.

n8n에서는 **HTTP Request 노드**로 보냅니다.

```
Method   POST
URL      <Discord 웹훅 주소>
Body     { "content": "보낼 메시지" }
```

여기서 걸린 제약이 **메시지 하나에 2000자**입니다. 기사 목록을 한 번에 다 담으면 이 선을 넘고, 그러면 잘리는 게 아니라 **요청 자체가 거부됩니다.**

그래서 Code 노드에서 2000자를 넘지 않게 미리 쪼개두고, Loop가 그 조각들을 차례로 보냅니다. **앞의 두 노드가 이 제약 하나 때문에 들어간 것입니다.**

웹훅 주소는 **그 자체가 인증 수단**입니다. 아는 사람은 누구나 그 채널에 글을 쓸 수 있으므로, 워크플로에 직접 적지 말고 n8n의 자격 증명(Credentials)에 넣어두는 편이 낫습니다.

</KnowledgeNote>
</KnowledgeList>

#### Ollama를 붙이는 자리

n8n에서 Ollama 연결은 **Base URL 하나로 끝납니다.**

```
http://ollama:11434
```

`localhost`가 아니라 **서비스 이름**입니다. 1절에서 본 그대로인데, 실제로 걸리는 자리가 여기입니다. 확인은 컨테이너 안에서 직접 해보면 됩니다.

```bash
docker exec n8n curl -s http://ollama:11434
```

그리고 여기서 앞 절의 방화벽 이야기가 이어집니다. **n8n이 이 주소로 부르기 때문에, Ollama를 호스트에 열어둘 이유가 없었던 것**입니다. 두 컨테이너 사이의 통신은 Docker 네트워크 안에서 끝나고 호스트 포트를 거치지 않습니다.

#### 이 파이프라인에 들어 있는 세 가지

결과는 Discord로 받았습니다. 이 파이프라인 자체는 대단한 게 아닙니다. 그런데 **비서가 갖춰야 할 세 가지가 전부 들어 있습니다.**

```
  ① 바깥의 정보를 가져오고        RSS Read
  ② 로컬 모델이 판단하고          Ollama
  ③ 나에게 도달한다              Discord
```

일정 관리 비서도 구조는 같습니다. ①이 RSS 대신 일정 데이터가 되고, ②가 "이월할지 지울지"를 판단하고, ③이 저에게 알림을 보냅니다. **다음 편에서 만들 것은 이 파이프라인의 각 자리를 바꿔 끼우는 일입니다.**

만드는 것 자체는 생각보다 쉬웠습니다. 노드를 늘어놓고 선으로 잇는 방식이라, 코드를 짜는 것보다 흐름이 눈에 잘 들어옵니다.

어려웠던 건 다른 쪽이었습니다. **지금 이 환경에 무엇이 부족한지를 파악하는 일**입니다. 처음 써보는 도구였고, 처음 만져보는 서버였습니다. 뭔가 잘 안 될 때 그것이 n8n 설정 문제인지, 컨테이너 네트워크 문제인지, 모델이 감당 못 하는 요청인지, 아니면 애초에 제가 잘못 이해한 것인지를 가려내는 데 대부분의 시간이 들어갔습니다.

이 편에서 세 번이나 같은 종류의 착각을 기록하게 된 것도 같은 이유입니다. 돌아가긴 하는데, **어디까지 제대로 돌아가는 건지 판단할 기준이 아직 제 안에 없었습니다.**

## 결론

Docker 위에 Ollama와 n8n을 올렸습니다. RSS를 읽어 로컬 모델이 정리하고 Discord로 보내는 흐름까지 이어졌습니다. **아직 비서는 아닙니다. 비서를 만드는 데 필요한 도구가 갖춰진 상태입니다.**

올리는 일은 compose 파일 하나와 명령 한 줄이었고, 나머지는 전부 확인하는 일이었습니다.

**방화벽은 우회당하고 있었습니다.** 기본 거부로 켜둔 ufw에 포트를 열고 접속이 되는 걸 보고 끝났다고 생각했는데, 애초에 ufw는 관여하고 있지 않았습니다. `ufw status`는 계속 안전하다고 답하는데 두 서비스가 모든 인터페이스에 열려 있었습니다. ufw와 싸우는 대신 **바인딩 주소를 좁히는 것**으로 해결했습니다.

**그리고 아직 터지지 않은 것이 하나 있습니다.** compose에 적어둔 IP가 **DHCP로 빌린 주소**였습니다. 주소가 바뀌는 날에만 터지는 종류라, netplan으로 고정 주소를 하나 더 붙여두었습니다. 방화벽이 "확인하지 않아서 몰랐던 것"이라면 이건 **확인할 대상이 아직 없었던 것**입니다.

**GPU 이야기는 이 글에서 빠져 있습니다.** 이 노트북을 서버로 고른 이유가 GPU였는데 결국 쓰지 못했고, 그 과정과 측정값은 [번외편](/blog/home-server-extra-gpu)에 따로 적었습니다. 이 글에 남는 숫자는 하나입니다. **초당 13토큰** — 대화하기에는 답답하지만 사람이 기다리지 않는 자동화에는 충분합니다. 이 제약이 다음 편의 설계 조건이 됩니다.

### 다음 편에서 할 일

```
  ① 외부 접속 경로        Cloudflare Tunnel로 밖에서도 닿게 만든다
  ② 보안 마무리           방화벽 대역 제한 · fail2ban의 실제 차단 동작 확인
  ③ 일정 데이터 연결       비서가 읽고 쓸 곳을 정한다
  ④ 판단 파이프라인        이월 · 삭제 · 오늘 마무리를 모델이 분류한다
```

①과 ②를 한 묶음으로 두는 데는 이유가 있습니다. 2편에서 미뤄둔 것들은 **밖에서 들어올 경로가 정해진 다음에야 제대로 막을 수 있습니다.** 어디로 들어올지 모르는 상태에서 규칙을 짜봐야, 경로를 만든 뒤에 다시 손대게 됩니다. 이번 편에서 `N8N_SECURE_COOKIE=false`로 낮춰둔 것도 그때 되돌려야 합니다.

그 밖에도 손대지 않은 것들이 있습니다. 931GB짜리 HDD는 여전히 비어 있고, 컨테이너가 죽었을 때 알려주는 장치도 없습니다. 하나씩 채워갈 생각입니다.

지금 그 노트북은 피아노 밑 거치대에 덮개를 닫은 채 세워져 돌고 있습니다. 며칠씩 잊고 지내다가 가끔 SSH로 붙어 상태를 봅니다. 서버가 잘 돌아간다는 건 존재를 잊게 된다는 뜻이기도 합니다.

몇 년째 열지 않던 노트북이 다시 일을 하고 있습니다. 아직은 RSS를 읽어 정리하는 정도지만, 다음 편에서는 제 일정을 챙기게 만들 생각입니다.
