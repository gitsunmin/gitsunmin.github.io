## 서론

[지난 편](/blog/home-server-02-security-docker)에서 문을 잠그고 Docker를 올렸습니다. 그릇은 준비됐습니다.

이번 편에서는 그 위에 **비서의 재료 두 가지**를 올립니다. 판단할 머리인 **Ollama**와, 그 머리를 정해진 시간에 움직이게 할 손인 **n8n**입니다.

그리고 중간에 **이 노트북을 고른 이유**를 꺼냅니다. 10년 된 노트북을 서버로 삼은 것은 GPU가 달려 있었기 때문인데, 정작 그동안 한 번도 쓰지 않고 있었습니다.

그리고 마지막에 둘을 한 번 이어봅니다. 비서를 만들기 전에, **재료가 서로 연결되는지**부터 확인하는 단계입니다.

컨테이너를 올려보고 나서야 알게 된 것도 둘 있습니다. 하나는 위에 적은 GPU이고, 다른 하나는 **켜져 있다고 믿은 방화벽**입니다.

## 본론

### 1. Ollama 설치와 모델 선택

#### Ollama를 띄우기

Ollama는 언어 모델을 내려받아 로컬에서 실행하고, HTTP API로 노출해주는 도구입니다. 모델 파일 관리, 양자화 형식, 메모리 배분 같은 것을 알아서 처리해줍니다.

```yaml
  ollama:
    image: ollama/ollama:latest
    container_name: ollama
    restart: unless-stopped
    gpus: all
    ports:
      - "127.0.0.1:11434:11434"
    volumes:
      - ./ollama:/root/.ollama
```

볼륨 연결이 중요합니다. 모델 파일은 수 GB 단위인데, 이걸 컨테이너 밖으로 빼두지 않으면 컨테이너를 다시 만들 때마다 모델을 새로 받게 됩니다.

모델은 SSD에 있습니다. 처음에는 용량이 넉넉한 HDD(`/data`)에 두는 게 맞다고 생각했지만, 모델은 호출할 때마다 통째로 메모리에 올라가는 구조라 저장장치 읽기 속도가 첫 응답 시간에 그대로 반영됩니다. 실제로 모델을 새로 올리는 순간의 로딩 시간은 25초였습니다. HDD였다면 더 걸렸을 겁니다.

```
1회차  total duration: 1m2.6s   load duration: 25.7s
2회차  total duration: 35.3s    load duration: 8.0ms
```

1회차와 2회차의 차이가 전부 모델 로딩입니다. 한 번 올라간 뒤에는 메모리에 머물러서 로딩 비용이 사라집니다. 다만 RAM이 8GB뿐이라 오래 놀면 내려가고, 다시 부를 때 25초를 또 기다립니다.

#### GPU를 컨테이너에 넘기기

모델이 올라갔으니 이제 속도를 봐야 합니다. 그런데 그 전에 확인할 것이 있었습니다. **이 노트북을 고른 이유가 GPU였는데, 그동안 그 이유를 한 번도 쓰지 않고 있었습니다.**

컨테이너 안에서 GPU를 확인해봤습니다.

```bash
docker exec ollama nvidia-smi
```
```
OCI runtime exec failed: "nvidia-smi": executable file not found in $PATH
```

컨테이너는 GPU의 존재조차 모르고 있었습니다. Ollama 로그를 보니 더 분명했습니다.

```
msg="inference compute" id=cpu library=cpu description=cpu total="7.1 GiB"
```

`library=cpu`. **설치한 날부터 계속 CPU로만 추론하고 있었습니다.** 에러도 경고도 없었습니다. Ollama는 GPU를 못 찾으면 조용히 CPU로 떨어지고, 그냥 느려질 뿐입니다. 확인하지 않으면 모르고 지나갑니다.

원인은 두 겹이었습니다.

**첫째, 호스트에 드라이버가 없었습니다.**

```bash
lsmod | grep -c nvidia
# 0
```

`ubuntu-drivers`에게 물어보니 다행히 지원 목록에 남아 있었습니다.

```
model    : GM107M [GeForce GTX 960M]
driver   : nvidia-driver-580 - distro non-free recommended
driver   : nvidia-driver-580-server - distro non-free
```

여기서 눈여겨볼 것이 있습니다. 시스템 저장소에는 595 브랜치 드라이버도 있는데, **이 GPU에는 580만 제시됩니다.** 960M은 Maxwell 세대(2015년)이고, 580이 Maxwell을 지원하는 마지막 브랜치입니다. 10년 된 하드웨어가 지원 목록의 끝자락에 겨우 걸려 있는 셈입니다. 몇 년 뒤에는 이 노트북으로 이 글을 다시 쓸 수 없을 겁니다.

추천은 `nvidia-driver-580`이지만 `-server` 변형을 골랐습니다. 이 노트북은 화면을 쓰지 않는 헤드리스 서버라 X 서버용 구성 요소가 필요 없습니다. **추천 로직은 일반 데스크탑을 가정합니다.** 용도가 다르면 추천을 따르지 않아도 됩니다.

```bash
sudo apt install -y nvidia-driver-580-server
sudo reboot
```

재부팅 후:

```
+-----------------------------------------------------------------------+
| NVIDIA-SMI 580.173.02      Driver Version: 580.173.02  CUDA Version: 13.0 |
|   0  NVIDIA GeForce GTX 960M      Off |    0MiB /   2048MiB |   0%      |
+-----------------------------------------------------------------------+
```

**VRAM 2048MiB.** 960M은 2GB 모델과 4GB 모델이 따로 있는데, 이 노트북은 2GB짜리였습니다. 이 숫자가 뒤에서 발목을 잡습니다.

덧붙이면, 이 재부팅에서 얻은 것이 하나 더 있습니다. 자동 재부팅을 켜지 않은 이유로 "컨테이너가 제대로 다시 올라오는지 검증한 적이 없다"고 적었는데, 여기서 검증됐습니다.

```
CONTAINER ID   IMAGE                     STATUS
5f1ec9a07797   docker.n8n.io/n8nio/n8n   Up 39 minutes
81ec121d2e25   ollama/ollama:latest      Up 39 minutes
```

`restart: unless-stopped`가 제 몫을 했습니다.

<KnowledgeList title="드라이버를 고르기 전에">
<KnowledgeNote term="lsmod | grep -c nvidia 가 0 이라는 것" kind="definition" defaultOpen>

`lsmod`는 **커널에 지금 올라와 있는 모듈 목록**을 보여줍니다(**l**i**s**t **mod**ules). 드라이버는 커널 모듈 형태로 로드되므로, 여기에 없으면 드라이버가 동작하고 있지 않다는 뜻입니다.

`grep -c`는 앞에서 본 대로 **개수만** 셉니다. 그래서 결과가 `0`이면 nvidia 관련 모듈이 하나도 없다는 뜻입니다.

여기서 헷갈리기 쉬운 것이 있습니다. **GPU가 인식되는 것과 드라이버가 있는 것은 다릅니다.**

```bash
lspci | grep -i nvidia     # 하드웨어가 꽂혀 있는가
lsmod | grep -c nvidia     # 그걸 쓸 드라이버가 올라와 있는가
```

첫 번째는 드라이버가 없어도 나옵니다. 메인보드가 장치를 보고 있다는 것뿐이기 때문입니다. 실제로 계산에 쓰려면 두 번째가 필요합니다.

</KnowledgeNote>
<KnowledgeNote term="ubuntu-drivers 와 -server 변형" kind="reason">

```bash
ubuntu-drivers devices
```

이 명령은 연결된 하드웨어를 훑어 **설치 가능한 드라이버 후보**를 알려줍니다. `recommended` 표시가 붙은 것이 추천입니다.

그런데 이 추천은 **일반 데스크탑을 가정합니다.** 화면에 그래픽을 출력하는 용도까지 포함해 고르기 때문에, X 서버 관련 구성 요소가 함께 딸려옵니다.

| 이름 | 용도 |
|---|---|
| `nvidia-driver-580` | 데스크탑용. 화면 출력용 구성 요소 포함 |
| `nvidia-driver-580-server` | 서버용. **연산에 필요한 것만** |

헤드리스 서버라면 `-server` 쪽이 맞습니다. 설치 용량이 작고, 화면을 쓰지 않으니 없어도 아쉬울 것이 없습니다. **추천은 참고일 뿐, 용도가 다르면 따르지 않아도 됩니다.**

드라이버 설치 후에는 **재부팅이 필요합니다.** 커널 모듈을 새로 올려야 하기 때문입니다. 설치 직후 `nvidia-smi`를 실행하면 아직 안 된다고 나오는 것이 정상입니다.

</KnowledgeNote>
</KnowledgeList>

**둘째, 컨테이너가 GPU를 볼 수 없었습니다.**

호스트에 드라이버가 있어도 컨테이너는 여전히 GPU를 못 봅니다. Docker는 기본적으로 장치 노드를 격리하고, 이 격리를 뚫어 GPU를 넘겨주는 것이 `nvidia-container-toolkit`의 역할입니다.

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg

curl -fsSL https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt update
sudo apt install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

<KnowledgeNote term="nvidia-container-toolkit 이 하는 일" kind="definition">

컨테이너는 **호스트의 장치 파일을 볼 수 없도록 격리**되어 있습니다. GPU도 장치 파일(`/dev/nvidia*`)로 존재하므로, 기본 상태로는 컨테이너 안에서 GPU가 아예 없는 것과 같습니다.

toolkit은 컨테이너가 뜨는 순간 끼어들어 **필요한 장치 파일과 드라이버 라이브러리를 컨테이너 안으로 넣어줍니다.** 그래서 컨테이너 이미지에 드라이버를 설치할 필요가 없습니다. 호스트의 드라이버를 빌려 쓰는 구조입니다.

설치 명령 중 낯선 것이 하나 있습니다.

```bash
... | sed 's#deb https://#deb [signed-by=...] https://#g'
```

`sed`는 문자열을 치환하는 명령이고, `s#찾을것#바꿀것#g`가 그 문법입니다. 보통 `s/…/…/`처럼 슬래시를 쓰는데, **바꿀 내용에 슬래시(`https://`)가 들어 있어서** 구분자를 `#`으로 바꾼 것입니다. NVIDIA가 배포하는 저장소 파일에 `signed-by=` 항목이 빠져 있어 그 자리에 끼워 넣는 작업입니다.

`nvidia-ctk runtime configure --runtime=docker`는 `/etc/docker/daemon.json`에 NVIDIA 런타임을 등록합니다. 등록만으로는 적용되지 않으므로 **`systemctl restart docker`가 반드시 뒤따라야 합니다.**

</KnowledgeNote>

그리고 compose에 한 줄을 더합니다.

```yaml
  ollama:
    image: ollama/ollama:latest
    gpus: all
```

이제 컨테이너 안에서 `nvidia-smi`가 뜹니다. 로그도 바뀌었습니다.

```
msg="gpu memory" id=0 library=CUDA available="1.5 GiB" free="1.9 GiB"
```

`library=cpu`에서 `library=CUDA`로. 성공한 것처럼 보였습니다.

#### `nvidia-smi`가 뜬다고 끝이 아니었다

같은 로그를 조금 더 내려 읽었습니다.

```
common_params_fit_impl: - CUDA0 (NVIDIA GeForce GTX 960M):  0 layers, 129 MiB used, 1831 MiB free
load_tensors: offloading 0 repeating layers to GPU
load_tensors: offloaded 0/36 layers to GPU
```

**36개 레이어 중 0개.** GPU를 인식했지만 실제로는 아무것도 올리지 않았습니다. 이유는 그 바로 위에 있었습니다.

```
msg="disabling multimodal projector offload" reason=limited-vram
```

당시 쓰던 `gemma4:e2b`는 이미지도 처리하는 멀티모달 모델입니다. 이미지 인코더(projector)가 따로 붙어 있는데, Ollama는 가용 VRAM 1.5GiB로는 이 구조가 들어가지 않는다고 판단해서 projector 오프로드를 끄고, 이어서 레이어도 하나도 올리지 않기로 결정했습니다.

드라이버를 깔고, 재부팅하고, toolkit을 붙이고, `nvidia-smi`까지 확인했는데 **추론은 여전히 100% CPU에서 돌고 있었습니다.**

측정해봤습니다. 같은 프롬프트로 각각 5회씩입니다.

| | eval rate 평균 | 범위 |
|---|---|---|
| GPU 연결 전 | 12.95 tok/s | 12.72 ~ 13.20 |
| GPU 연결 후 | 13.24 tok/s | 13.07 ~ 13.33 |

**차이 2.2%.** 측정 오차입니다. `offloaded 0/36`이 숫자로 확인된 셈입니다.

그런데 프롬프트 처리 속도를 보고 한 번 더 놀랐습니다.

| | prompt eval rate |
|---|---|
| GPU 연결 전 | 168 ~ 179 tok/s |
| GPU 연결 후 | 119 ~ 131 tok/s |

5회가 전부 깔끔하게 갈립니다. **GPU를 연결했더니 프롬프트 처리가 30% 느려졌습니다.**

단서는 아까 그 로그 줄에 있었습니다.

```
CUDA0 (GTX 960M): 0 layers, 129 MiB used, 1831 MiB free
```

레이어는 하나도 안 올렸는데 **129MiB를 쓰고 있습니다.** 연산 버퍼는 GPU에 잡아둔 상태입니다. 실제 계산은 전부 CPU가 하는데, CUDA 백엔드와 동기화하는 비용만 얹힌 것입니다. 얻은 것 없이 부담만 추가된, 가장 나쁜 조합이었습니다.

여기서 배운 것은 하나입니다. **`nvidia-smi`가 출력되는 것과 모델이 GPU를 쓰는 것은 전혀 다른 문제입니다.** 대부분의 설치 안내는 `nvidia-smi`가 뜨면 끝난 것처럼 적고 넘어갑니다. 실제로 확인해야 할 줄은 이것입니다.

```bash
docker logs ollama 2>&1 | grep "offloaded"
```

<KnowledgeList title="로그와 측정값 읽기">
<KnowledgeNote term="offload 와 레이어" kind="definition" defaultOpen>

언어 모델은 **레이어**라는 층이 수십 개 쌓인 구조입니다. 추론은 입력을 1번 레이어부터 마지막 레이어까지 차례로 통과시키는 일입니다.

**오프로드**(offload)는 그 레이어들을 **CPU에서 GPU로 옮겨 싣는 것**을 말합니다. 전부 옮길 필요는 없고, VRAM에 들어가는 만큼만 옮긴 뒤 나머지는 CPU가 처리하는 부분 오프로드도 가능합니다.

```
offloaded 0/36 layers to GPU     ← 36개 중 0개. 전부 CPU
offloaded 17/17 layers to GPU    ← 전부 GPU
```

**속도는 이 비율을 대체로 따라갑니다.** GPU가 인식되었는지가 아니라 **몇 개를 올렸는지**가 성능을 결정합니다. 그래서 확인해야 할 줄이 `nvidia-smi`가 아니라 이 줄입니다.

Ollama는 VRAM이 부족하다고 판단하면 **경고 없이 올리는 개수를 줄입니다.** 실패하는 것보다 느리게라도 돌아가는 쪽을 택하는 설계인데, 그래서 조용히 CPU로 떨어져 있어도 사용자는 알 수 없습니다.

</KnowledgeNote>
<KnowledgeNote term="eval rate 와 prompt eval rate 는 다른 것을 잽니다" kind="definition">

Ollama가 내놓는 두 숫자는 서로 다른 구간을 측정합니다.

| 지표 | 재는 것 |
|---|---|
| `prompt eval rate` | 내가 **입력한 문장을 읽어들이는** 속도 |
| `eval rate` | 모델이 **답을 만들어내는** 속도 |

성격이 다릅니다. 입력을 읽는 단계는 전체를 한꺼번에 처리할 수 있어서 **병렬 처리에 유리하고**, 그래서 GPU 효과가 크게 납니다. 답을 만드는 단계는 앞 글자가 나와야 다음 글자를 만들 수 있어 **순차적**입니다.

체감 속도는 보통 `eval rate` 쪽입니다. 글자가 찍히는 속도가 그것입니다.

이 절에서 **`eval rate`는 그대로인데 `prompt eval rate`만 30% 느려진 것**이 단서가 됐습니다. 레이어를 하나도 안 올렸으니 답을 만드는 속도는 그대로일 수밖에 없고, 그런데도 GPU에 129MiB를 잡아두고 동기화 비용만 치르고 있어서 읽는 쪽만 손해를 본 상태였습니다.

</KnowledgeNote>
<KnowledgeNote term="docker logs 의 2>&1 은 무엇인가" kind="definition">

```bash
docker logs ollama 2>&1 | grep "offloaded"
```

프로그램의 출력은 두 갈래로 나뉩니다.

- **표준 출력**(1번) — 정상적인 결과
- **표준 에러**(2번) — 에러와 진단 메시지

`|` 파이프는 **표준 출력만** 넘깁니다. 그런데 많은 프로그램이 진단 메시지를 표준 에러로 내보내고, Ollama의 로딩 로그도 그쪽입니다. 그래서 그냥 `docker logs ollama | grep …`을 하면 **찾는 줄이 없다고 나옵니다.** 로그가 없어서가 아니라 파이프에 실리지 않아서입니다.

`2>&1`은 **2번을 1번으로 합치라**는 뜻입니다(`&`는 "번호"라는 표시). 합치고 나면 파이프가 둘 다 넘깁니다.

`grep`이 아무것도 못 찾았을 때 이걸 먼저 의심해보면 시간을 아낍니다.

</KnowledgeNote>
</KnowledgeList>

`offloaded 0/36 layers to GPU`를 보기 전까지, 저는 GPU를 쓰고 있다고 믿고 있었습니다.

그렇다면 2GB VRAM에 들어가는 모델은 무엇인가. 이제 그 이야기입니다.

#### 모델을 고르면서 했던 착각

Gemini를 자주 쓰고 있어서 같은 계열인 Gemma로 이어갔습니다. 이게 표면적인 이유입니다.

그런데 솔직히 말하면, 후보를 좁히는 과정에서 **중국에서 만든 모델을 먼저 걸러냈습니다.** 개인정보가 새어 나간다는 이야기를 들은 적이 있었기 때문입니다. Qwen이나 DeepSeek은 성능 대비 크기가 작아서 이런 저사양 환경에 자주 추천되는데도, 목록에서 그냥 지웠습니다.

이 판단은 **절반만 맞았습니다.**

우려 자체는 근거가 있습니다. 2025년 4월, 개인정보보호위원회는 DeepSeek이 한국 이용자의 개인정보를 동의 없이 국외로 이전한 사실을 확인하고 시정을 권고했습니다. 기기·네트워크·앱 정보뿐 아니라 **이용자가 입력한 프롬프트 내용까지** ByteDance 계열사인 Volcano Engine으로 전송됐고, 영향 범위는 약 150만 명으로 추정됐습니다. 국내 앱마켓에서는 이미 2월에 신규 다운로드가 중단된 상태였습니다.

- [개인정보위, 딥시크에 "해외이전 개인정보 파기" 시정·권고명령 — 바이라인네트워크](https://byline.network/2025/04/25-427/)
- [South Korea says DeepSeek transferred user data to China and the U.S. without consent — CNBC](https://www.cnbc.com/2025/04/24/south-korea-says-deepseek-transferred-user-data-to-china-us-without-consent.html)

그런데 이 사건은 **DeepSeek이라는 서비스**의 이야기입니다. 앱에 입력한 데이터가 그 회사 서버로 갔다는 것입니다.

제가 지금 하려는 일은 다릅니다. Ollama로 받는 것은 **가중치 파일**입니다. 한 번 내려받고 나면 추론은 이 노트북 안에서만 일어납니다. 컨테이너에서 나가는 트래픽이 없고, 프롬프트가 도달할 서버도 없습니다. 어느 나라 회사가 공개한 가중치든, 로컬에서 도는 이상 데이터를 보낼 방법 자체가 없습니다.

**같은 이름을 쓰는 두 가지가 전혀 다른 물건이었습니다.** 하나는 남의 서버에서 도는 서비스이고, 하나는 내 디스크에 있는 파일입니다.

이 서버를 만든 이유가 바로 그것이었는데도, 정작 모델을 고를 때는 그 원리를 잊고 브랜드로 판단하고 있었습니다. 클라우드에 보내기 싫어서 집에 서버를 세워놓고, 그 서버 안에서 돌릴 파일을 국적으로 걸러낸 셈입니다.

결과적으로 Gemma를 쓰고 있고 그 선택 자체를 후회하지는 않습니다. 익숙한 계열이라 응답 형태를 예상하기 쉽고, 한국어도 무난합니다. 다만 **이유가 틀렸다는 건 기록해둡니다.** 다음에 모델을 바꿀 때는 국적이 아니라 크기와 품질로 고를 겁니다.

#### 8GB와 2GB 사이에서

받아둔 모델은 두 개입니다.

```bash
docker exec ollama ollama list
# gemma4:e2b
# gemma4:e4b
```

`e2b`, `e4b`의 `e`는 유효 파라미터(effective) 수를 뜻합니다. 전체 파라미터는 더 많지만 추론할 때 실제로 활성화되는 양이 2B, 4B 수준이라는 의미입니다. 메모리를 적게 쓰면서 큰 모델의 품질에 가까워지려는 구조입니다.

이 노트북에는 두 개의 벽이 있습니다.

```
  RAM   8GB   ─ OS + Docker + n8n이 먼저 쓰고 남은 자리
                Ollama가 인식한 가용 메모리: 7.1 GiB
  VRAM  2GB   ─ Ollama가 실제로 쓸 수 있다고 판단한 양: 1.5 GiB
```

RAM 쪽은 생각보다 여유가 있습니다. 7.1GiB면 4B급 모델도 CPU에서는 돌아갑니다. 문제는 **VRAM 1.5GiB**입니다. 앞 절에서 `offloaded 0/36`의 원인으로 확인한 그 숫자입니다.

그래서 지금 쓰는 모델은 GPU에 올라가지 못합니다. 2GB 안에 들어가는 1B급 텍스트 전용 모델로 바꾸면 상황이 달라지겠지만, 그러면 이번에는 품질을 포기해야 합니다.

**속도를 얻으려면 더 작은 모델로 내려가야 하고, 품질을 지키려면 CPU로 돌려야 합니다.** 이 교환을 어느 쪽으로 끊을지는 비서가 실제로 어떤 판단을 해야 하는지 정해진 다음에야 결정할 수 있습니다. 다음 편의 숙제로 남겨두었습니다.

참고로 반대 방향도 시험해봤습니다. 한 단계 큰 `gemma4:e4b`입니다.

| | e2b | e4b |
|---|---|---|
| eval rate | 13.0 tok/s | 6.95 tok/s |
| 모델 로딩 | 25.7초 | 1분 41초 |
| prompt eval rate | 120~180 tok/s | 4.17 tok/s |

생성 속도가 절반인 것은 파라미터가 두 배이니 예상 범위입니다. 문제는 나머지입니다. 프롬프트 처리 속도가 **30배 이상 떨어졌습니다.** 이건 계산이 느린 게 아니라 메모리가 부족해 디스크와 오가고 있다는 신호입니다. 로딩에 1분 41초가 걸린 것도 같은 이야기입니다.

한가할 때는 e4b도 그럭저럭 돌아갑니다. 하지만 비서가 실제로 일할 때는 n8n 워크플로가 함께 움직이고, 그때 이 여유는 사라집니다. **8GB의 벽은 평소가 아니라 바쁠 때 드러납니다.**

#### 13 tok/s는 쓸 만한 속도인가

지금 `gemma4:e2b`의 생성 속도는 **초당 13토큰**입니다.

이 숫자를 감각으로 옮기면, 사람이 소리 내어 읽는 속도와 비슷합니다. 화면 앞에 앉아 대화하기에는 답답합니다. 질문 하나에 30초에서 1분이 걸립니다.

그런데 만들려는 것은 대화 상대가 아닙니다. **정해진 시간에 혼자 돌아가는 비서**입니다. 아침에 오늘 일정을 정리하고, 저녁에 남은 항목을 훑는 작업입니다. 그 시간에 저는 화면을 보고 있지 않습니다. 1분이 걸리든 3분이 걸리든 결과만 제때 도착하면 됩니다.

**로컬 LLM의 쓸모를 가르는 기준이 여기 있었습니다.** 즉시 응답이 필요한 용도에는 맞지 않고, 사람이 기다리지 않는 자동화에는 충분합니다. 그리고 제가 만들려는 것은 정확히 후자입니다.

품질은 아직 검증하지 못했습니다. 속도는 숫자로 나왔지만, **2B급 모델이 실제로 일정을 판단하고 정리할 수 있는지**는 다음 편에서 확인해야 할 문제입니다.

### 2. n8n 설치

#### 왜 n8n인가

n8n은 화면에서 노드를 연결해 자동화 흐름을 만드는 도구입니다. Zapier나 Make와 같은 종류인데, 결정적인 차이가 하나 있습니다. **직접 호스팅할 수 있습니다.**

Zapier에 데이터를 흘려보내면 그 데이터는 그쪽 서버를 거칩니다. 클라우드에 보내지 않으려고 집에 서버를 세워놓고, 정작 자동화 도구가 데이터를 밖으로 보내면 앞뒤가 맞지 않습니다. n8n은 같은 서버 안에서 돌면서 옆 컨테이너의 Ollama를 호출합니다. **데이터가 이 노트북을 벗어나지 않습니다.**

#### compose에 추가하기

```yaml
  n8n:
    image: docker.n8n.io/n8nio/n8n
    container_name: n8n
    restart: unless-stopped
    ports:
      - "<서버 고정 IP>:5678:5678"
    environment:
      - N8N_PORT=5678
      - N8N_PROTOCOL=http
      - NODE_ENV=production
      - GENERIC_TIMEZONE=Asia/Seoul
      - TZ=Asia/Seoul
      - N8N_SECURE_COOKIE=false
    volumes:
      - ./n8n:/home/node/.n8n
    depends_on:
      - ollama
```

`./n8n` 볼륨에 워크플로와 자격 증명이 저장됩니다. 이 디렉터리를 잃으면 만들어둔 워크플로가 전부 사라집니다.

두 서비스를 한 파일에 둔 이유는 **서로를 필요로 하기 때문**입니다. n8n은 Ollama를 호출하고, 둘은 같은 네트워크 안에 있어야 합니다. Compose는 프로젝트마다 기본 네트워크를 자동으로 만들어주기 때문에, 같은 파일에 선언하기만 하면 **서비스 이름이 그대로 호스트명**이 됩니다.

```
http://ollama:11434
```

n8n 컨테이너 안에서 이 주소로 Ollama에 접근합니다. **`localhost`가 아닙니다.**

<KnowledgeList title="compose 를 읽기 전에">
<KnowledgeNote term="컨테이너 안의 localhost 는 다른 곳입니다" kind="caution" defaultOpen>

컨테이너는 각자 자기만의 네트워크 공간을 가집니다. 그래서 **컨테이너 안에서 `localhost`는 그 컨테이너 자신**을 가리킵니다. 호스트도 아니고 옆 컨테이너도 아닙니다.

호스트에서는 잘 되던 것이 컨테이너 안에서만 안 되는 상황이 여기서 나옵니다.

```bash
curl http://localhost:11434                   # 호스트에서 — 됩니다
docker exec n8n curl http://localhost:11434   # n8n 안에서 — 안 됩니다
```

n8n 컨테이너 안에 11434를 듣고 있는 것이 없기 때문입니다. 부를 때는 **서비스 이름**을 씁니다.

```bash
docker exec n8n curl http://ollama:11434      # 됩니다
```

Compose가 프로젝트마다 네트워크를 하나 만들고 **서비스 이름을 그 네트워크의 호스트명으로 등록**해주기 때문에 가능한 일입니다. 별도로 IP를 알아낼 필요가 없고, 컨테이너를 다시 띄워 IP가 바뀌어도 이름은 그대로입니다.

호스트를 가리켜야 한다면 `host.docker.internal`이라는 별도의 이름을 씁니다.

</KnowledgeNote>
<KnowledgeNote term="restart 정책 네 가지" kind="definition">

컨테이너가 죽거나 서버가 재부팅됐을 때 어떻게 할지를 정합니다.

| 값 | 동작 |
|---|---|
| `no` | 아무것도 하지 않습니다. 기본값 |
| `on-failure` | **비정상 종료일 때만** 다시 띄웁니다 |
| `always` | 항상 다시 띄웁니다. `docker stop`으로 직접 멈춰도 **재부팅하면 다시 뜹니다** |
| `unless-stopped` | 항상 다시 띄우되, **직접 멈춘 것은 그대로 둡니다** |

`always`와 `unless-stopped`의 차이가 실제로 갈리는 지점은 재부팅입니다. 점검하려고 컨테이너를 내려둔 상태에서 서버를 재부팅하면, `always`는 내 의도를 무시하고 다시 띄웁니다. `unless-stopped`는 내려둔 채로 둡니다.

이 서버는 `unless-stopped`를 씁니다. 홈서버는 전원이 나갔다 들어오는 일이 있어서 **자동으로 복구되어야 하지만**, 제가 일부러 멈춘 것까지 되살아나면 곤란하기 때문입니다.

</KnowledgeNote>
</KnowledgeList>

첫 접속 시 브라우저에서 오너 계정을 만듭니다. 예전 버전에서 쓰던 `N8N_BASIC_AUTH_*` 환경변수는 이제 필요 없고, n8n 자체 사용자 관리로 대체됐습니다.

#### 처음 쓴 설정에서 틀렸던 것들

동작은 했지만, 나중에 문제가 될 것들이 섞여 있었습니다.

**`N8N_HOST=0.0.0.0`을 지웠습니다.** 처음에는 "모든 IP의 접근을 허용한다"는 뜻으로 알고 넣었는데, 아니었습니다. `N8N_HOST`는 바인딩 주소가 아니라 **n8n이 자기 주소를 만들 때 쓰는 기준값**입니다. 이 상태로 두면 n8n이 생성하는 웹훅 주소가 `http://0.0.0.0:5678/...`이 됩니다. 아무도 접속할 수 없는 주소입니다. 접속 허용 범위를 정하는 건 지난 편의 ufw와 포트 바인딩이고, 이 값이 아니었습니다.

**`TZ=Asia/Seoul`을 추가했습니다.** 원래 `GENERIC_TIMEZONE`만 넣어두었는데, 이건 n8n 스케줄러가 쓰는 시간대입니다. 컨테이너의 **시스템 시간**은 여전히 UTC였습니다. 로그 타임스탬프가 9시간 어긋나고, 워크플로 안에서 `new Date()`로 날짜를 계산하면 자정 근처에서 하루가 밀립니다. **매일 남은 일정을 정리하는 비서를 만들 계획이라면 이건 치명적입니다.** 두 값을 모두 지정해야 합니다.

**`version: '3.8'`을 지웠습니다.** Compose V2부터 이 필드는 무시되고 경고만 출력합니다.

**`depends_on`은 그대로 두되, 기대를 바꿨습니다.** 처음에는 "Ollama가 켜진 것을 확인한 뒤 n8n이 실행된다"고 이해했는데, `depends_on`은 **컨테이너가 시작됐는지만** 봅니다. Ollama 프로세스가 요청을 받을 준비가 됐는지는 확인하지 않습니다. 실제로 기다리게 하려면 `healthcheck`와 `condition: service_healthy`가 필요합니다. 지금은 n8n이 Ollama를 부르는 시점이 기동 직후가 아니라 워크플로 실행 시점이라 문제가 되지 않지만, 알고 두는 것과 모르고 두는 것은 다릅니다.

#### Docker는 ufw를 우회합니다

두 컨테이너가 다 떴으니 이제 밖에서 어떻게 보이는지 확인할 차례입니다. 이 서버의 ufw는 **들어오는 것을 기본 거부**로 두고 있습니다. 열어준 적 없는 포트라면 막혀 있어야 하는데, 이런 상태였습니다.

```
CONTAINER   PORTS
n8n         0.0.0.0:5678->5678/tcp
ollama      0.0.0.0:11434->11434/tcp
```

`0.0.0.0` — **모든 네트워크 인터페이스에 열려 있습니다.** ufw에서 무엇을 막아두었든 상관없이 열려 있습니다.

이유는 Docker가 포트를 게시하는 방식에 있습니다. `ports: - "5678:5678"`을 선언하면 Docker는 iptables의 `DOCKER` 체인에 규칙을 직접 넣습니다. 그리고 **이 체인은 ufw가 관리하는 체인보다 먼저 평가됩니다.** ufw는 자기가 모르는 규칙이 앞에 끼어든 것을 알지 못하고, 사용자는 `ufw status`만 보고 안전하다고 착각합니다.

특히 문제가 되는 쪽은 Ollama입니다. **11434 포트에는 인증이 없습니다.** 집 안 네트워크의 아무 기기나 접속해서 모델을 부르고, 지우고, 새로 받을 수 있습니다.

<KnowledgeList title="포트가 열리는 구조">
<KnowledgeNote term="ports 표기 읽는 법" kind="definition" defaultOpen>

compose의 `ports`는 콜론으로 나뉜 자리마다 뜻이 다릅니다.

| 표기 | 뜻 |
|---|---|
| `"5678"` | 컨테이너 포트만. 호스트 쪽은 **아무 번호나 임의로** 배정됩니다 |
| `"5678:5678"` | `호스트:컨테이너`. 호스트의 **모든 인터페이스**(`0.0.0.0`)에 엽니다 |
| `"127.0.0.1:11434:11434"` | `호스트IP:호스트:컨테이너`. **지정한 주소에만** 엽니다 |

앞자리를 생략하면 `0.0.0.0`이 됩니다. 즉 **아무 생각 없이 `"5678:5678"`이라고 쓰면 모든 곳에 여는 것**입니다. 대부분의 예제가 이렇게 적혀 있고, 그래서 대부분의 홈서버가 이 상태로 돌아갑니다.

두 자리는 서로 달라도 됩니다. `"8080:5678"`은 컨테이너의 5678을 호스트의 8080으로 내보낸다는 뜻입니다. 컨테이너 안쪽 번호는 그 프로그램이 정한 것이라 바꿀 수 없지만, 호스트 쪽은 마음대로 고를 수 있습니다.

</KnowledgeNote>
<KnowledgeNote term="왜 ufw 로는 막을 수 없는가" kind="definition">

리눅스의 방화벽은 **규칙을 순서대로 검사하는 체인** 구조입니다. 위에서부터 훑다가 맞는 규칙을 만나면 거기서 결정이 끝나고, 뒤는 보지 않습니다.

ufw는 이 체인을 다루기 쉽게 감싼 **도구**일 뿐이고, 실제 규칙은 그 아래 `iptables`(요즘은 `nftables`)에 들어갑니다. 문제는 Docker도 같은 곳에 규칙을 넣는데, **ufw의 규칙보다 앞자리에 넣는다**는 것입니다.

```
들어온 패킷
   ↓
DOCKER 체인    ← Docker가 넣은 규칙. 여기서 통과 결정이 나면 끝
   ↓
ufw 체인       ← 여기까지 오지 않습니다
```

그래서 `ufw deny 5678`을 넣어도 아무 일이 일어나지 않습니다. **규칙이 틀린 게 아니라 도달하지 않습니다.** 그리고 `ufw status`는 자기가 아는 규칙만 보여주므로, 목록은 여전히 안전해 보입니다.

Docker가 이렇게 하는 데는 이유가 있습니다. 컨테이너는 수시로 뜨고 지는데, 그때마다 사용자의 방화벽 설정을 건드리는 것보다 자기 영역을 따로 관리하는 편이 안전하기 때문입니다. **버그가 아니라 설계입니다.** 그래서 고치려 들지 말고, 애초에 좁게 여는 쪽이 맞습니다.

`DOCKER-USER` 체인에 규칙을 넣어 제어하는 방법도 있지만, 바인딩 주소를 좁히는 쪽이 훨씬 단순하고 실수할 여지가 적습니다.

</KnowledgeNote>
</KnowledgeList>

해결책은 ufw와 싸우는 것이 아니라, **포트를 게시할 때 바인딩 주소를 좁히는 것**입니다.

```yaml
  ollama:
    ports:
      - "127.0.0.1:11434:11434"      # 서버 자신에게만
  n8n:
    ports:
      - "<서버 고정 IP>:5678:5678"      # 집 안에서 브라우저로 접속
```

Ollama는 호스트에 열어둘 이유가 아예 없습니다. 앞에서 본 대로 n8n은 같은 Docker 네트워크 안에서 `http://ollama:11434`로 부르기 때문에, 호스트를 거칠 일이 없습니다. 인터페이스를 특정하면 Docker가 iptables에 넣는 규칙 자체가 좁아지므로, ufw와 충돌할 일이 사라집니다.

```
n8n      <서버 고정 IP>:5678->5678/tcp
ollama   127.0.0.1:11434->11434/tcp
```

`0.0.0.0`이 사라졌습니다. 지금은 포트포워딩이 없어서 인터넷에 노출되지는 않지만, **마지막 편에서 Cloudflare Tunnel을 붙일 때 이 상태로 두면 안 됩니다.**

한편 ufw에는 5678과 11434를 여는 규칙이 아직 남아 있습니다. 이제 이 규칙들은 **아무 일도 하지 않습니다.** 애초에 Docker가 우회하고 있었으니 막은 적이 없고, 바인딩을 좁힌 지금은 열어줄 것도 없습니다. 규칙이 있으니 뭔가 관리되고 있다는 인상만 남습니다. 아무것도 듣고 있지 않은 80·443 규칙도 마찬가지입니다.

#### 그런데 이 한 줄이 다음 장애를 예약해두었습니다

방금 compose에 IP를 직접 적었습니다. 그러고 보니 지난 편에서 한 번 더 적었습니다. 맥의 `~/.ssh/config`에 넣은 `HostName`입니다.

**설정 파일에 IP를 적는 순간 그 주소가 안 바뀐다고 가정한 것**인데, 확인해본 적이 없었습니다.

```bash
ip -4 addr show eno1 | grep inet    # eno1 은 인터페이스 이름. `ip -br addr` 로 확인
```
```
inet <DHCP로 받은 IP>/24 metric 100 ... scope global dynamic eno1
```

`dynamic`. **공유기에게 빌려 쓰는 주소**입니다. 임대가 만료되거나 공유기를 재시작하면 다른 주소를 받을 수 있습니다.

그러면 무슨 일이 생기냐면, Docker는 **존재하지 않는 주소에는 바인딩할 수 없습니다.**

```
Error: bind: cannot assign requested address
```

n8n 컨테이너가 뜨지 못합니다. `restart: unless-stopped`도 소용없습니다. 그저 재시작을 반복할 뿐입니다. 그리고 이건 오늘 확인해봐야 알 수 없는 종류의 문제입니다. **지금은 아무 이상이 없고, 조건이 갖춰지는 날에만 터집니다.** 앞의 사례들이 "확인하지 않아서 몰랐던 것"이라면, 이건 확인할 대상이 아직 존재하지 않는 경우입니다.

정공법은 공유기에서 MAC 주소에 IP를 예약하는 것인데, 공유기 관리자 페이지 로그인이 되지 않아 서버 쪽에서 해결했습니다. 다만 흔한 방법인 `dhcp4: false` + 고정 IP는 쓰지 않았습니다. **적용하는 순간 주소가 바뀌면서 SSH가 끊기고**, 헤드리스 서버라 잘못되면 노트북을 직접 열어야 하기 때문입니다.

대신 DHCP를 그대로 두고 주소를 하나 더 붙였습니다.

```yaml
# /etc/netplan/00-installer-config.yaml
    eno1:
      dhcp4: true
      addresses:
        - <서버 고정 IP>/24
```

```bash
sudo netplan generate && sudo netplan apply
```

```
inet <서버 고정 IP>/24 scope global eno1
inet <DHCP로 받은 IP>/24 metric 100 scope global secondary dynamic eno1
```

DHCP로 받은 쪽은 공유기가 주는 주소라 바뀔 수 있고, 새로 붙인 쪽은 서버가 스스로 갖는 주소라 바뀌지 않습니다. 게이트웨이와 DNS는 DHCP가 계속 제공하므로 따로 적을 것도 없습니다. **기존 접속이 끊기지 않으니 잠길 위험도 없습니다.**

<KnowledgeList title="netplan 을 만지기 전에">
<KnowledgeNote term="netplan 이란" kind="definition" defaultOpen>

Ubuntu에서 **네트워크 설정을 담당하는 계층**입니다. YAML 파일에 원하는 상태를 적어두면, netplan이 그것을 실제로 네트워크를 제어하는 도구(서버에서는 보통 `systemd-networkd`)의 설정으로 **번역해서 넘깁니다.**

설정 파일은 `/etc/netplan/` 아래에 있고, 이름은 설치 방식에 따라 다릅니다.

```bash
ls /etc/netplan/
```

**들여쓰기에 민감합니다.** YAML이라 공백 두 칸이 틀리면 다른 뜻이 되고, 탭 문자는 아예 허용되지 않습니다. 그래서 적용 명령이 두 단계로 나뉘어 있습니다.

| 명령 | 하는 일 |
|---|---|
| `netplan generate` | 설정을 **번역만** 해봅니다. 문법이 틀리면 여기서 멈춥니다 |
| `netplan apply` | 실제로 적용합니다 |
| `netplan try` | 적용하되, **120초 안에 엔터를 안 누르면 자동으로 되돌립니다** |

`generate`를 먼저 하는 것은 sshd에서 `sshd -t`를 먼저 하는 것과 같은 이유입니다. **원격 접속을 끊어먹을 수 있는 설정은 항상 검사부터** 합니다.

원격으로 네트워크를 바꿀 때는 `netplan try`가 더 안전합니다. 설정이 잘못돼 접속이 끊기면 아무것도 하지 않아도 2분 뒤에 원래대로 돌아옵니다.

</KnowledgeNote>
<KnowledgeNote term="ip addr 출력에서 봐야 할 단어" kind="definition">

```
inet <서버 고정 IP>/24 scope global eno1
inet <DHCP로 받은 IP>/24 metric 100 scope global secondary dynamic eno1
```

| 단어 | 뜻 |
|---|---|
| `inet` | IPv4 주소. IPv6은 `inet6`으로 나옵니다 |
| `/24` | 넷마스크. 앞 24비트가 같으면 같은 네트워크라는 뜻 |
| `scope global` | 외부와 통신 가능한 주소. `scope host`는 자기 자신용(`127.0.0.1`) |
| `dynamic` | **DHCP로 빌린 주소.** 만료되면 바뀔 수 있습니다 |
| `secondary` | 이 인터페이스의 **두 번째 이후** 주소 |
| `metric` | 경로 우선순위. 낮을수록 먼저 씁니다 |

여기서 결정적인 단어가 **`dynamic`**입니다. 이게 붙어 있으면 그 주소는 **언젠가 바뀝니다.** compose 파일이나 설정에 적어 고정된 값처럼 쓰고 있다면, 그날이 장애가 나는 날입니다.

`-4`는 IPv4만 보겠다는 옵션입니다. 붙이지 않으면 IPv6 주소가 함께 나와 출력이 길어집니다.

</KnowledgeNote>
</KnowledgeList>

고정 주소를 아무 번호나 고르면 안 되는 이유도 있습니다. 공유기는 DHCP로 나눠줄 주소의 **범위**를 정해두고 그 안에서 배분하는데, 그 범위 안의 주소를 고정으로 박으면 서버가 꺼져 있는 동안 다른 기기가 같은 주소를 받아 **IP 충돌**이 납니다. 공유기는 그 주소가 예약됐다는 걸 모르기 때문입니다. 그래서 **DHCP 범위 밖의 번호**를 골라야 합니다. 범위는 공유기 관리자 페이지에서 확인할 수 있습니다.

#### 첫 파이프라인 — RSS에서 Discord까지

설치가 끝났으니 흐름이 실제로 이어지는지 확인해야 합니다. 비서를 만들기 전에, **재료가 서로 연결되는지**부터 보는 단계입니다.

```
  [Schedule Trigger]   매일 아침 10시
          ▼
  [RSS Read]           Google News RSS
          ▼
  [Aggregate]          흩어진 항목을 하나로 모음
          ▼
  [Code / JavaScript]  기사 정리 · 메시지 조립
          ▼
  [Loop]  ──▶  [HTTP Request]   Discord 웹훅으로 나눠 전송
```

`Loop`가 들어간 이유가 있습니다. Discord 메시지에는 글자 수 상한이 있어서, 기사를 한 번에 다 보내면 잘리거나 요청이 거부됩니다. Code 노드에서 상한을 넘지 않게 쪼개두고, Loop가 그 조각들을 차례로 보냅니다.

**이런 제약은 만들기 전에는 보이지 않습니다.** 워크플로를 그릴 때는 "기사를 Discord로 보낸다" 한 줄이었는데, 실제로 돌려보니 노드가 두 개 더 필요했습니다.

Ollama 연결은 Base URL 하나로 끝납니다.

```
http://ollama:11434
```

`localhost`가 아닙니다. 컨테이너 안에서 `localhost`는 그 컨테이너 자신을 가리킵니다. 두 서비스가 같은 Compose 파일에 있으면 기본 네트워크를 공유하므로, **서비스 이름이 그대로 호스트명**이 됩니다. 호스트에서는 `curl http://localhost:11434`가 잘 되는데 n8n 안에서만 안 되는 상황이 나오면 대부분 이 문제입니다.

결과는 Discord 웹훅으로 받았습니다. HTTP Request 노드로 웹훅 URL에 POST를 보내면 채널에 메시지가 뜹니다.

이 파이프라인 자체는 대단한 게 아닙니다. 그런데 **비서가 갖춰야 할 세 가지가 전부 들어 있습니다.**

```
  ① 바깥의 정보를 가져오고        RSS Read
  ② 로컬 모델이 판단하고          Ollama
  ③ 나에게 도달한다              Discord
```

일정 관리 비서도 구조는 같습니다. ①이 RSS 대신 일정 데이터가 되고, ②가 "이월할지 지울지"를 판단하고, ③이 저를 찔러줍니다. 다음 편에서 만들 것은 이 파이프라인의 각 자리를 바꿔 끼우는 일입니다.

만드는 것 자체는 생각보다 쉬웠습니다. 노드를 늘어놓고 선으로 잇는 방식이라, 코드를 짜는 것보다 흐름이 눈에 잘 들어옵니다.

어려웠던 건 다른 쪽이었습니다. **지금 이 환경에 무엇이 부족한지를 파악하는 일**입니다. 처음 써보는 도구였고, 처음 만져보는 서버였습니다. 뭔가 잘 안 될 때 그것이 n8n 설정 문제인지, 컨테이너 네트워크 문제인지, 모델이 감당 못 하는 요청인지, 아니면 애초에 제가 잘못 이해한 것인지를 가려내는 데 대부분의 시간이 들어갔습니다.

이 시리즈에서 세 번이나 같은 종류의 착각을 기록하게 된 것도 같은 이유입니다. 돌아가긴 하는데, **어디까지 제대로 돌아가는 건지 판단할 기준이 아직 제 안에 없었습니다.**

## 결론

여기까지가 비서가 살 집을 짓는 과정이었습니다.

10년 된 HP 노트북에 Ubuntu Server를 올리고, SSH와 방화벽의 기본을 잡고, Docker 위에 Ollama와 n8n을 띄웠습니다. RSS를 읽어 로컬 모델이 요약하고 Discord로 보내는 흐름까지 확인했습니다. **아직 비서는 아닙니다. 비서를 만들 재료가 갖춰진 상태입니다.**

그리고 이 노트북을 고른 이유였던 GPU를 여기서 처음 꺼내 썼습니다. **드라이버를 깔고, toolkit을 붙이고, `nvidia-smi`까지 확인했는데도 추론은 여전히 100% CPU에서 돌고 있었습니다.** `nvidia-smi`가 출력되는 것과 모델이 GPU를 쓰는 것은 다른 문제였고, 확인해야 할 줄은 `offloaded 0/36 layers`였습니다. 에러는 한 줄도 나지 않았습니다.

숫자로 남은 것이 있습니다. 2GB VRAM에는 지금 쓰는 모델이 들어가지 않고, 8GB RAM 안에서는 e4b가 버겁습니다. 초당 13토큰은 대화하기에는 답답하지만 **사람이 기다리지 않는 자동화에는 충분합니다.** 이 제약이 다음 편의 설계 조건이 됩니다.

컨테이너를 올리고 나서 알게 된 것이 하나 더 있습니다. **기본 거부로 켜둔 방화벽을 Docker가 우회하고 있었습니다.** `ufw status`는 계속 안전하다고 답하는데, 실제로는 두 서비스가 모든 인터페이스에 열려 있었습니다. ufw와 싸우는 대신 포트를 게시할 때 **바인딩 주소를 좁히는 것**으로 해결했고, 그 과정에서 compose에 적어둔 IP가 DHCP로 빌린 주소였다는 것도 드러났습니다. 지금은 문제가 없고 **주소가 바뀌는 날에만 터지는** 종류였습니다.

틀린 이유로 고른 것도 하나 기록해두었습니다. 클라우드에 보내기 싫어서 집에 서버를 세워놓고, 정작 그 서버 안에서 돌릴 **가중치 파일**을 국적으로 걸러냈습니다. 결과는 나쁘지 않았지만 이유는 틀렸습니다.

### 다음 편에서 할 일

```
  ① 외부 접속 경로        Cloudflare Tunnel로 밖에서도 닿게 만든다
  ② 보안 마무리           방화벽 대역 제한 · fail2ban의 실제 차단 동작 확인
  ③ 일정 데이터 연결       비서가 읽고 쓸 곳을 정한다
  ④ 판단 파이프라인        이월 · 삭제 · 오늘 마무리를 모델이 분류한다
```

①과 ②를 한 묶음으로 두는 데는 이유가 있습니다. 2편에서 미뤄둔 것들은 **밖에서 들어올 경로가 정해진 다음에야 제대로 막을 수 있습니다.** 어디로 들어올지 모르는 상태에서 규칙을 짜봐야, 문을 낸 뒤에 다시 손대게 됩니다.

그 밖에도 손대지 않은 것들이 있습니다. 931GB짜리 HDD는 여전히 비어 있고, 컨테이너가 죽었을 때 알려주는 장치도 없습니다. 하나씩 채워갈 생각입니다.

지금 그 노트북은 피아노 밑 거치대에 덮개를 닫은 채 세워져 돌고 있습니다. 며칠씩 잊고 지내다가 가끔 SSH로 붙어 상태를 봅니다. 서버가 잘 돌아간다는 건 존재를 잊게 된다는 뜻이기도 합니다.

몇 년째 열지 않던 노트북이 다시 일을 하고 있습니다. 아직은 RSS를 읽어 요약하는 정도지만, 다음 편에서는 제 일정을 챙기게 만들 생각입니다.
